# Repository review: Python, custom formats, and the binary

This review found correctness problems at the boundaries between the lossless
parser, semantic storage, and custom printing. The existing separation remains
useful: syntax recovery can serve inspection tools without pretending that
unknown operations have complete semantics. The main remaining integration
gap is that Python's operation-shape registry cannot be configured in the CLI.

The review covered the registry and custom grammar, lowering and semantic
verification, printing, query evaluation, semantic editing, Python handles and
type declarations, and packaging/CI configuration. It included local
reproductions and the Rust and Python suites. This is not a claim of complete
MLIR dialect compatibility or an exhaustive audit of every parser production.

## Fixed during this review

| Finding | Result |
| --- | --- |
| A generic `arith.addi` with zero operands and one result panicked in custom printing. | Built-in assembly printing checks operand/result counts and its applicable verifier before printing; unsupported operations use generic form. |
| Custom printing dropped operation locations, properties, and regions unsupported by the selected assembly. | These cases use generic output. Round-trip regressions check preservation of semantic data. |
| A typed generic constant printed as `arith.constant 7 : i32 : i32`; string-valued module/function names could produce invalid custom syntax. | Those representations remain generic. |
| The CLI rewrote only the first anonymous `module {`, leaving named, commented, and nested shorthand inconsistent. | Core, proving, and declarative registries containing `builtin.module` handle shorthand in the parser. The CLI rewrite and offset adjustment were removed. |
| An unknown custom sibling enabled best-effort lowering and hid unrelated semantic errors from CLI counts. | The CLI rejects semantic lowering diagnostics even when unknown custom syntax was recovered. |
| Python dense-array elements had values but empty `spelling` strings. | Their scalar spellings are exposed. |
| Python file-print methods reported validation failures as `OSError`. | Validation failures raise `ValueError`; actual I/O failures remain `OSError`. Existing-file preflight checks remain covered. |
| Operation-shape APIs advertised `Mapping` but rejected `UserDict` and mapping proxies. | Both constructors consume mappings, matching the type declarations. |

The user-facing contract is documented in
[custom-formats.md](../docs/custom-formats.md).

## 1. Quoted symbol paths and lookup — P1

Reproduction:

```python
import zirium

document = zirium.parse_text(
    '"test"() {a = @"a::b"} : () -> ()'
).lower_strict().document
attribute = document.operation_table().operation(0).attribute_by_name("a")
print(attribute.symbol_value)       # Includes unwanted quote characters.
print(document.canonical_bytes())  # Inserts an @ inside the quoted name.
```

`semantic/values.rs::resolve_attribute` splits symbol paths with
`split("::")`, even inside a quoted component. `Document::lookup_symbol` and
`semantic/verify.rs::ensure_symbol_index` split them again. `normalize_symbol`
strips delimiters without decoding escapes. Consequently, changing the Python
accessor alone would leave canonical output and lookup inconsistent.

Work:

1. Define one representation for symbol-path components, including whether
   stored components are decoded names or exact spellings. Preserve the
   distinction between one component containing `::` and a nested reference.
2. Use the lexer or one shared quoted-string-aware routine to construct paths.
   Remove splitting and rejoining from lookup and diagnostic construction.
3. Decode symbol-definition keys and reference keys consistently. Print each
   component with the appropriate MLIR escaping.
4. Keep the existing convenience string accessors, but decide how callers pass
   an unambiguous nested path to lookup. A list of components may be preferable
   to another ad hoc string grammar.

Acceptance: `@"a::b"`, `@outer::@"a::b"`, escaped quotes, and escaped UTF-8
round-trip through Rust and Python. Equivalent escaped spellings resolve to the
same definition. A literal `::` within one name never becomes a nested lookup.
CLI closure should resolve the supported `func.call` forms consistently.

## 2. Share registry configuration with the binary — P1

Python and Rust can assign `FUNC_LIKE` and `CALL_LIKE` shapes to caller-named
operations. `main.rs` always chooses `DialectRegistry::proving()` and has no
registry arguments. Installing the Python package also does not install the
Cargo binary. These are separate entry points, which the usage guide now makes
explicit.

Shapes were originally added for inspection, as described in
[the existing custom-format plan](extended-mlir-support/01-custom-formats.md).
That plan explicitly excluded verification, symbol resolution, and custom
printing. `query.rs::evaluate_closure` currently requires descriptors and
special-cases `func.call`, `cf.br`, and `cf.cond_br`; merely loading shapes will
not make closure work for vendor calls.

The implementation and design are now recorded in [shared registry configuration](registry-configuration.md):
JSON read through Serde, explicit built-in names and operation-shape records,
`zirium --registry FILE`, and matching Python `from_file` / `from_config`
constructors, including Pydantic models and multiple configurations. The design includes validation, CLI argument behavior,
implementation steps, and the boundary between syntax shapes and semantic
roles. A [sample configuration](examples/registry.json) accompanies it.

## 3. Element spellings through aliases — P2

Reproduction:

```python
import zirium

document = zirium.parse_text(
    '#a = [1, 2]\n"test"() {a = #a} : () -> ()'
).lower_strict().document
attribute = document.operation_table().operation(0).attribute_by_name("a")
assert attribute.element(0).integer_value == 1
assert attribute.element(0).spelling == ""  # Current behavior.
```

The semantic value is resolved, but the top-level spelling remains `#a`.
`SemanticAttribute::element` reparses that spelling as an array or dictionary
and substitutes an empty string when it cannot find the element. This also
prevents reliable recursive inspection of nested aliased containers and makes
such elements unsuitable as sources for edit attribute specifications.

Work:

1. Define whether an element's `spelling` promises exact source text or a valid
   semantic spelling when no independent source span exists. An alias has no
   element text at the use site.
2. Prefer a core attribute-formatting API for a semantic fallback. Keep exact
   child spellings where available; avoid a second MLIR parser in the binding.
3. Remove the silent empty-string fallback for valid values. Ensure an element
   used to construct `AttributeSpecHandle` has matching value and spelling.

Acceptance: scalar, array, and dictionary aliases support recursive element
inspection after the original `File` has been dropped. Attribute specs made
from those elements can be committed and printed without losing their values.

## Validation

Local checks use macOS arm64 and CPython 3.14. The full Rust workspace tests pass on stable and Rust 1.88. Clippy with
warnings denied, doc tests, Ruff, and the Python type checker pass. Python
reports 69 passed and 2 skipped. The two platform-dependent `/dev/full` Python tests are

all supported Python versions were not rerun.
